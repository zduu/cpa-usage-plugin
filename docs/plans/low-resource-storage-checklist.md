# 插件低内存、低负载改造：方案审查与工作清单

审查基线：`4eea7c586fbc9554012ed4568f839c6d834dd776`。
状态：代码层面的设计审查完成；实现、驱动验证、迁移演练及性能验收尚未进行。
本清单用于后续实施，不表示数据库后端已经可用或可以立即发布。

## 1. 审查结论

“本地数据库保存数据 + 有容量预算的内存缓存 + 增量汇总 + 分批后台任务”方向可行。
它可以保留现有统计、筛选、历史修复、精确计价、导入导出功能，减少常驻内存及全量扫描。
这是统计存储层的较大改造，不是简单更换文件格式；具体性能收益必须实测。

建议优先验证 SQLite。插件内嵌数据库，不要求用户安装数据库服务；驱动选择须通过现有五个平台的共享库构建与实际装载验证。
历史冷查询、重新计价和大导出可能变慢，磁盘 I/O 会增加，不能承诺所有操作同时更快。

不采用以下方式实现本次目标：缩短现有数据保留期限、关闭历史精确计价、删除账本信息、降低导出上限、静默合并不同客户端身份。
冷数据是仍属于现有保留范围、但不常驻内存的数据；超过 `retention_days` 的数据仍按原来的统计淘汰语义处理。
永久归档及任意期限历史查询属于另一个功能，不能借本次改造悄悄改变保留规则。

## 2. 功能影响和兼容边界

| 功能 | 必须保持的结果 | 实施约束 |
| --- | --- | --- |
| 原生 usage 统计 | 每个真实请求的数量、token、成功失败、延迟、TTFT 不变 | 接收、提交、查询可见性要明确；不能因为异步队列而静默丢数或让新数据暂时消失 |
| 看板与筛选 | API、模型、来源、凭证、客户端 key、时间范围的结果和联动不变 | 汇总加速仅用于能够精确回答的查询；边界时间和复杂筛选从索引数据补算 |
| 健康网格与趋势 | 桶粒度、时区、成功失败和成本口径不变 | 保留时间戳偏移、合成时间标记及滚动范围语义，不能用每日汇总近似所有查询 |
| 明细与账本 | `max_details_per_model` 的可见明细语义不变；账本继续参与统计 | “缓存中没有”不等于“数据淘汰”；账本不得冒充完整事件出现在列表里 |
| 历史计价 | provider 价格优先级、时段、星期、时区、缓存 token 口径及 models.dev 刷新不变 | 保留逐请求计价依据；同一响应内价格与汇总必须使用相同有效版本 |
| 历史修复、导入和重放 | 现有去重、Claude 缓存修复、旧归因修复、协议关联规则不变 | 缓存修复仍按现有显式开关启用；修复记录与全部派生统计事务更新 |
| 导入导出 | 既有 JSON、JSONL、CSV、gzip、计数、截断、过滤与完整备份语义不变 | 新传输接口可以追加，旧接口继续兼容；不以静默截断实现省内存 |
| 缓存与状态 | ETag/304、失效、错误响应和健康状态保持正确 | 存储故障必须显式可见，不能返回成功的空历史数据 |

### 两个不能隐瞒的限制

1. `storage_enabled: false` 代表不持久化。保留任意数量的逐请求数据、完全不写磁盘、同时保持固定低内存，三者无法兼得。
   保留现有内存模式；数据库模式只用于用户已启用持久化的场景。不开持久化时只能优化缓存和临时分配，不能承诺历史数据规模无关的内存占用。
2. 现有管理 ABI 和整包导入导出无法仅靠内部流式编码获得端到端恒定内存。
   优先追加可校验的分块下载和上传路径，并让内置看板使用它们；旧接口保留兼容及已有容量规则，单独测量其峰值。
   浏览器可能仍需组装最终文件，不能把服务端节省的内存误报为全链路节省。若需改宿主才能实现某种传输方式，必须列为阻塞条件。

## 3. 推荐实现边界

- 磁盘为数据库模式的权威数据源，保存完整明细、精简账本、记录身份、必要旧聚合残差和版本信息。
- 内存仅保存预算内的近期数据、查询结果和待提交数据；对单条大小、字节数、条数、并发数分别计量。
- 对数据库页缓存、连接数、临时排序、映射内存、WAL、任务暂存文件设置并验证资源策略；不能只控制 Go heap。
- 增量汇总避免每次查询扫描全部记录。高基数来源、凭证、客户端分组也存盘，避免其内存随记录增长。
- 单写入协调器批量提交；队列同时受字节数和条数预算约束。持续写入速度超过磁盘能力时，不能同时保证无丢失、无限接收和固定资源；必须测量并报告容量边界，明确背压和故障策略。
- 提交记录、汇总及处理进度同事务完成。查询的可见进度必须一致；如保留待提交覆盖层，它也必须有预算、精确合并且在重启后不产生重复。
- 冷查询按索引读取；分页使用稳定顺序和游标，时间戳相同也不能重复或漏项。
- 导出冻结数据版本与价格版本，优先在短期一致性读事务内分批生成磁盘文件，文件生成后释放事务再下载。
  限制长读事务和导出并发，处理 WAL 膨胀；不能仅冻结时间上界或最大 ID 就认为更新、删除不会影响快照。
- 改价重算使用分批计算和版本化汇总，处理重算期间的新请求、删除、到期、导入和再次改价；完成后原子发布。
  优先保持现有同步接口承诺。若重算无法在现有管理超时内完成，应先验证版本化查询方案；异步任务及 UI 状态属于需要单独确认的交互变化，不能默认纳入“功能不变”。

## 4. 能否继承升级

可以设计为继承现有配置和磁盘数据的升级，目标是不要求修改或重编译 CPA、不更换插件 ID、不要求手动重新导入。
此结论是迁移设计可行，不是迁移已验证通过。发布前必须满足下面的门槛。

- 保持 `storage_path` 解析规则。在原目录旁创建新数据库和迁移状态，原 JSONL、快照、价格文件及稳定 hash salt 保留。
- 识别旧单文件、日期分片、旧版本快照、带 `accounting` 的新快照，以及仅剩聚合但无逐请求信息的数据。
- 按旧恢复语义处理快照与分片覆盖关系。真实记录与仅剩聚合的差额分别导入，避免重复相加；缺失的逐请求时间、身份不能凭空恢复。
- 大快照采用增量解析与数据库暂存，不能先调用旧的全量内存恢复再整体搬进数据库；JSONL 分批迁移。
- 使用来源指纹、事务内迁移游标和明确的记录来源标识保证可重入。不能给实时 usage 套一个全局去重唯一键，误删字段相同但真实发生两次的请求。
- 初次迁移在开始接收 usage 前完成一致性切换。若耗时超过宿主初始化允许范围，先验证有持久化增量日志的在线迁移方案，不能直接丢弃迁移期间的数据或无限排队。
- 迁移校验通过后提交完成标记，再启用数据库。区分未开始、迁移中、已完成及不兼容 schema；禁止每次启动重复导入。
- 中断、磁盘满、权限失败时保留旧数据和可续传状态；不执行旧格式文件清理，不把“数据库为空”当作迁移完成。
- 迁移前原文件可以恢复迁移时刻的数据；升级后新写入的数据不在旧文件里。
  无损降级需要先生成旧版可读的兼容快照及增量并校验，且目标版本应支持相应 `accounting` 格式；仅替换旧插件二进制不构成无损回滚。
- SQLite 启用 WAL 后不能只复制主数据库文件作为备份。采用一致性备份机制，生成清单、校验和及恢复验证；旧备份不在每次启动时自动加载。
- 插件按宿主支持的正常关闭、更新、重新加载流程升级，不承诺无需重启的热替换。

## 5. 实施工作清单

以下均为待办，按阶段顺序执行。任一阶段门槛失败，先修订方案，再推进依赖阶段。

- [ ] 固定基线提交与测试环境，记录请求接收、统计可见、价格更新返回、导入导出和关闭行为。
- [ ] 准备 10 万、100 万请求数据，包含低/高维度数量、长错误文本、请求头、迟到记录、重复时间戳、账本及旧聚合残差。
- [ ] 测量稳定期及峰值 heap、CPA 进程 RSS、CPU、GC、磁盘写入、启动耗时、请求回调和各查询 p95/p99。

### P2：旧数据迁移与可恢复升级

- [ ] 在迁移各边界模拟终止和重启，验证不重复、不漏记、可以续传且内存不随输入文件整体增长。

阶段门槛：迁移前后功能结果等价，所有数据差异都有明确旧规则依据；无损回滚路径已实测。

- [ ] 保持时段、星期、时区、provider、缓存计价及合成时间语义；实现改价一致性方案及并发追赶校验。
- [ ] 移植历史修复与去重，用数据库暂存避免全量构造指纹 map；保持现有修复开关和身份边界。
- [ ] 验证 prices 保存失败、models.dev 刷新失败、数据库不可用、队列满及关闭期间的行为。

阶段门槛：既有功能回归通过，前后端价格与计数一致；不能仅验证全局总量而漏掉筛选后的差异。

### P4：导入导出与后台低负载

- [ ] 分批生成 JSON/JSONL/CSV/gzip 导出，冻结数据和价格，覆盖迟到上报、改价、修复及删除并发。
- [ ] 实现追加的分块传输接口和内置看板兼容路径，验证下载完整性、取消、重试、认证、临时文件生命周期及浏览器占用。
- [ ] 完整统计备份也采用分批生成；大文件导入分块上传并在数据库暂存校验，保留旧导入接口及原子性语义。
- [ ] 旧整包接口单独测峰值，明确其 ABI 限制；不得宣传所有旧端点都已具备固定内存。
- [ ] 限制后台并发与每批工作量；避免长期读事务拖住 WAL 回收，处理磁盘空间不足和超时。
- [ ] 用定时器按最近到期任务调度；空闲时减少唤醒，仍按配置完成可靠写入和同步。
- [ ] 以增量存储及一致性备份替代周期全量快照，验证不会悄悄削弱异常退出保护。

阶段门槛：大导出生成及新传输路径不再同时持有全部记录，后台任务不会导致写入持续积压。

### P5：验收、文档与发布

- [ ] 运行 Go race/vet、JavaScript、更新脚本、原生 CPA ABI 及五个平台构建测试。
- [ ] 使用 P0 相同数据和负载对照，建议把“100 万请求稳定期插件增量 RSS 至少降低 50%”作为初始候选门槛，P0 后按机器和基线固定最终数值，未实测前不承诺。

- [ ] 测量数据库原生内存、OS 页缓存与 CPA 进程 RSS，报告总磁盘占用、写放大和增长趋势；不能只汇报 Go heap。
- [ ] 长时间压测验证内存无持续漂移、队列可回落、WAL/临时文件可回收、数据核对通过。
- [ ] 更新配置字段说明、升级迁移、首次启动耗时、备份恢复、降级及数据库故障排查文档。
- [ ] 先通过明确选择的数据库后端验证，再考虑持久化用户的自动迁移发布；未启用持久化的用户不自动写盘。
- [ ] 记录版本、发布说明、迁移演练及性能报告，全部门槛通过后再提交实现并发布升级。
