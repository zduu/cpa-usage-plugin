# 单容器低资源优化施工清单（临时）

日期：2026-09-09。
代码基线：`74c3c099c532652fd267a64942e4dc7676c24181`，插件版本 `2.6.4`。
状态：施工草案；以下实现与验收事项均待完成。本次仅创建文档，不代表优化已实施或数据库后端已可用。

目标：在只运行一个 CPA Docker 容器、功能保持兼容、使用体验不降低的前提下，降低常驻及峰值内存、CPU 和垃圾回收压力。

存储兼容与历史迁移细节参考[原存储方案审查](low-resource-storage-checklist.md)。实施顺序和验收以本清单及本次用户约束为准；旧文档中的收益百分比和延迟退化候选值不作为本次验收标准。

## 1. 固定约束

- 部署只有一个 CPA 容器；统计插件、数据库引擎和后台任务均在 CPA 进程内运行，不新增数据库、缓存或任务服务容器。
- SQLite 引擎随插件交付，用户不需要安装数据库服务；数据沿用 `./data:/CLIProxyAPI/data` 挂载。
- 改造范围在插件内，保持插件 ID、宿主 ABI、已有管理接口和配置语义，不要求修改或重编译 CPA。
- 原生 usage 仍是唯一计数来源。请求数、成功失败、各类 token、延迟、TTFT、端点和流式元数据的现有语义保持兼容。
- 保持保留天数、可见明细条数、精简账本、导出容量和历史精确计价；真实重复请求继续保留，客户端身份继续精确区分。
- 保持看板筛选、排序、翻页、健康网格、趋势、币种切换、价格设置和导入导出的交互与结果。
- 保持当前前台 30 秒、后台 300 秒的轮询调度，以及手动刷新和切回页面的及时刷新行为。
- 保持请求记录的查询可见性、价格更新返回时的统计一致性、导入原子性，以及既有 flush、fsync 和恢复保障。
- `storage_enabled: false` 继续使用原有内存统计模式，不自动把 usage 历史写入数据库；既有价格文件及导出临时文件的行为保持兼容。
- 现有平台支持继续保留：Linux amd64/arm64、macOS amd64/arm64、Windows amd64。

目标部署结构：

```text
一个 CPA Docker 容器
└── CPA 进程
    └── usage-dashboard-zduu 插件
        ├── usage 接收、统计查询、内嵌看板
        ├── 有预算的缓存、后台写入、导入导出
        └── 内嵌 SQLite（持久化模式）

宿主机 ./data  <──挂载──>  容器 /CLIProxyAPI/data
```

## 2. 已观察到的开销与本机参考值

| 代码位置 | 当前行为 | 施工方向 |
| --- | --- | --- |
| `go/stats.go`：`invalidateSummaryLocked` | 每次记录使事件索引及查询缓存整体失效 | 索引增量维护，按数据、价格及查询依赖失效 |
| `go/stats.go`：`buildSummaryWithoutDetailsForRangeLocked`、`QueryAPIDetailForClientAPIAt` | 范围摘要和接口详情逐条读取明细及账本，主要计算位于统计锁内 | 时间分段汇总、边界精确补算、缩短持锁时间 |
| `go/stats.go`：`Snapshot`、`writeStorageSnapshotFile` | 复制全部统计数据，再整体 JSON 编码 | 一致版本下分批编码，持久化模式采用增量事务 |
| `go/dashboard_export_jobs.go`：`captureEventExport`、`handleDashboardEventsExportDownload` | 导出先复制全部匹配事件，下载再整体读取文件 | 分批生成文件，并单独优化分块传输 |
| `go/accounting.go`、`go/stats.go` | 完整明细和精简账本常驻内存 | 历史数据、身份索引和高基数汇总存盘 |
| `go/stats.go`：`storageWorkerLoop` | 每 100ms 检查后台任务到期状态 | 按最近到期时间唤醒 |
| `go/dashboard/script.js`：`rerender` | 数据变化后更新多个面板 | 按面板依赖局部更新，保持刷新频率 |

2026-09-09 在 Apple M1、macOS arm64、Go 1.26.4 上运行现有 10 万条查询基准的参考结果：

| 基准 | 单次耗时 | 单次分配 |
| --- | ---: | ---: |
| `BenchmarkSummaryWithoutDetails100k`，主要命中摘要缓存 | 18.54 µs | 100,230 B |
| `BenchmarkSummaryRange7d100k`，每次重建 7 天摘要 | 59.20 ms | 408,152 B |
| `BenchmarkQueryEvents100k`，保留索引、清除结果缓存 | 2.15 ms | 465,052 B |
| `BenchmarkQueryEventsColdModelIndex100k`，重建模型索引 | 6.18 ms | 2,251,152 B |
| `BenchmarkQueryEventsCached100k`，命中事件结果缓存 | 0.124 ms | 225,208 B |

这些是现有测试数据分布下的本机结果，不是 Docker 或生产环境的性能承诺。`B/op` 是操作分配量，不是常驻内存；不同基准的查询语义和缓存状态不同，不能直接当作优化前后对比。正式施工须补充容器基线。

## 3. 实施顺序与完成记录

先完成 P0，再推进 P1、P2、P3；之后完成 P4、P5 的存储验证及迁移，最后完成 P6 并进行 P7 整体验收。P4 的驱动可行性验证可在 P0 后提前开展，以尽早发现交付限制。

每项勾选完成时附上：相关变更、验证命令或复现步骤、结果、性能对照和遗留问题。阶段门槛未通过时，先修订该阶段方案，不把问题带入默认升级路径。

### P0：单容器基线与功能契约

- [ ] 固定 CPA 镜像版本或 digest、插件提交、架构、CPU/内存配额、Docker 版本、磁盘类型、挂载方式及配置；对照时保持一致。
- [ ] 固定数据集与生成种子：10 万、100 万条请求，分别覆盖低/高基数模型、来源、凭证、客户端身份，以及保留窗口内的精简账本。
- [ ] 补充迟到记录、同时间戳、真实重复请求、失败文本、响应头、时段及跨日计价、旧聚合残差等边界数据。
- [ ] 保存现有统计、筛选、事件顺序、价格更新、导入导出和重启恢复的期望结果，形成兼容对照样本。
- [ ] 在同一单容器环境测量无插件与有插件的空闲、持续写入、突发写入、多看板访问、改价、导入导出、保留清理和重启恢复。
- [ ] 记录 Go heap、进程 RSS、容器内存及文件缓存、CPU、GC、磁盘 I/O、请求回调与查询 p50/p95/p99；浏览器另测内存、长任务、刷新和下载耗时。
- [ ] 固定资源目标、交互时延、启动时间和误差范围；记录冷热缓存结果并重复测量。收益门槛须在看优化结果之前确定，体验指标不允许超出已记录测量误差的退化。

完成条件：已有可重复运行的单容器基线、兼容样本、资源预算和验收表。

### P1：增量索引、缓存与过期处理

涉及：`go/stats.go`、`go/accounting.go`、相关查询及保留策略测试。

- [ ] 梳理新增、迟到上报、元数据补充、导入、重放、历史修复、过期、配置及改价对索引和缓存的影响矩阵。
- [ ] 为内部记录引用建立稳定身份或稳定分段位置，保留现有排序和同时间戳行为；避免索引引用因切片移动、淘汰或修复而失效。
- [ ] 对实际使用的 API、模型、来源、凭证索引进行增量插入和删除，替换每次 usage 后的整体清空与重建；避免全量维护无查询需求的索引。
- [ ] 分离记录、聚合、价格和币种版本，按依赖更新缓存及 ETag；时间窗口推进、参数变化和错误路径也要正确失效。
- [ ] 对查询缓存及索引记录实际字节开销；通过共享不可变数据或有界的序列化结果缓存减少重复复制，同时保证调用方修改不会污染其他请求。
- [ ] 按时间索引或有序分段定位到期记录，增量扣减统计并释放引用；迟到的已过期记录仍按现有规则处理。
- [ ] 验证缓存命中、未命中和持续写入交错查询，覆盖并发读写、重复时间戳、价格改变及保留边界，并比较锁等待、分配和请求延迟。

完成条件：查询结果、排序和失效行为与基线一致；持续写入后的查询减少索引重建和分配，记录回调不出现可测的性能退化。

### P2：范围摘要、接口详情及计价增量化

涉及：`go/stats.go` 的范围摘要、接口详情、成本汇总及价格更新流程。

- [ ] 设计时间分段及所需维度的精确汇总；只维护实际存在且需要的组合，汇总及索引共同计入资源预算。
- [ ] 新增、补充、修复、导入、过期时同步更新相应汇总；完整时间段直接合并，边界段按真实请求时间精确补算。
- [ ] 复用范围汇总回答模型、来源、凭证和客户端筛选；不能精确覆盖的条件由索引补算，禁止近似结果代替现有统计。
- [ ] 拆分接口详情中的汇总、错误分布和最近事件查询，复用 P1 索引及汇总，保持各部分取自一致数据版本。
- [ ] 保留 provider 优先级、星期、跨午夜、时区、缓存读写和合成时间语义；价格变动只重算实际受影响的数据与汇总。
- [ ] 在不可变分段或一致版本基础上缩短统计锁内工作，处理计算期间的新写入及再次改价；保持价格接口返回时的现有一致性，不改为用户等待另一项异步任务。
- [ ] 对照全量与各筛选结果、健康网格、趋势、金额及 ETag，复测范围摘要和接口详情的 CPU、内存分配与 p95/p99。

完成条件：范围统计精确且及时，查询不再普遍按全部历史逐条重算；新增汇总占用符合预算。

### P3：后台调度、编码分配与页面更新

涉及：`go/stats.go`、`go/dashboard/script.js`、`go/dashboard/helpers.js`。

- [ ] 将 writer 固定 100ms 检查改为最近任务到期定时器；队列到达、配置变更和关闭仍能及时唤醒。

- [ ] 根据分配剖析复用编码及批处理缓冲；设置可保留容量上限，避免一次大任务让池长期占用大块内存。
- [ ] 对页面面板建立数据依赖标记，减少无变化区域的 DOM 和图表重建；保留已有 ETag、隐藏页轮询和失败退避机制。
- [ ] 保持语言、币种、筛选、展开状态、焦点、滚动和手动刷新行为；切回可见页面仍及时展示最新状态。
- [ ] 分别测量单容器空闲唤醒和浏览器长任务、内存；报告后台收益与浏览器收益，避免混为同一项服务器优化。

完成条件：写入与刷新时限保持兼容，空闲 CPU、临时分配或页面重绘开销出现可复现下降。

### P4：内嵌 SQLite 原型与资源预算

涉及：存储后端边界、`go/go.mod`、`go/register.go`、构建工作流和 `tests/stock-host`。

- [ ] 比较驱动的 Go 1.26 支持、许可证、共享库符号、二进制体积及原生内存；固定版本，确保插件包含所需引擎，部署不新增运行服务或要求用户安装数据库。
- [ ] 验证五种现有目标的构建和 ABI；重点在 Linux amd64/arm64 的单 CPA 容器中加载，核对当前镜像的 libc 及动态链接兼容性。
- [ ] 在真实数据挂载目录验证权限、文件锁、WAL、checkpoint 和异常恢复；明确支持的文件系统与单路径实例边界。
- [ ] 设计明细、账本、稳定身份、旧聚合残差、迁移进度、必要索引和汇总版本 schema，使用真实筛选条件检查查询计划。
- [ ] 为近期缓存、查询缓存、待提交队列、数据库页缓存、连接数、临时排序、映射内存、WAL 和导出暂存设定并测量预算。
- [ ] 实现单写入协调器及批量事务；记录、汇总和提交进度共同提交，新请求及时可见。若使用待提交覆盖层，限定其字节数并验证精确合并与恢复。
- [ ] 验证队列积压、磁盘满、写入错误、长读事务、取消和关闭行为；在目标负载下不丢记录、不持续积压、不降低已有可靠性。
- [ ] 对同一数据集比较原型与内存后端的冷热查询、写入延迟、CPU、RSS 和磁盘开销；原型过不了体验及资源门槛时先调整设计。

完成条件：插件内嵌数据库在单容器中可用，资源预算可测，原型支持继续接入正式数据路径。

### P5：后端接入、旧数据迁移与回退

涉及：`go/stats.go`、`go/accounting.go`、历史修复、配置及价格持久化流程。

- [ ] 接入实时记录、查询、元数据补充、历史修复、导入、计价和保留清理，使明细、账本、身份索引及高基数汇总无需全量常驻内存。
- [ ] 保留未开启持久化时的原行为；已开启持久化时继承路径解析、保留规则和稳定 hash salt，避免切换后重新分组客户端身份。
- [ ] 按旧恢复语义识别单文件 JSONL、日期分片、各版本快照、`accounting` 和仅剩聚合的残差，正确处理快照与分片覆盖及重放。
- [ ] 分批解析迁移数据，使用来源指纹、事务内游标及完成标记保证中断后可继续；不能先完整加载旧数据到内存再整体搬运。
- [ ] 在接收新 usage 前完成一致切换并测量初始化时限；如需在线迁移，先验证有持久化增量日志的方案，保证迁移期间记录不遗漏、不重复。
- [ ] 保留原文件；模拟损坏数据、权限错误、磁盘满及迁移中断，验证可重入与校验失败时的可恢复状态。
- [ ] 核对明细、账本、聚合残差、全部统计维度及计价结果；普通重启不重复导入，也不误读旧备份。
- [ ] 验证 SQLite 一致性备份和恢复；无损降级须把升级后新增数据转为目标旧版可读且支持相应账本语义的格式并核对，不能只替换旧插件文件。

完成条件：正常升级继承配置和历史数据，无需用户手动重新导入；迁移、重启恢复和回退演练通过。

### P6：快照、导入导出及分块传输

涉及：`go/stats.go`、`go/dashboard_export_jobs.go`、`go/management.go`、`go/main.go`、前端导入导出逻辑。

- [ ] 为导出冻结真实数据版本和价格版本；持久化模式使用一致性读取，内存模式使用有预算的不可变分段或等价方案。只冻结时间上界或最大 ID 不足以隔离后续修复、改价和删除。
- [ ] 分批生成 JSON、JSONL、CSV 和 gzip 文件，消除全部匹配记录的额外复制；保持事件、成本、字段、排序、计数、截断规则和原有下载文件结构。
- [ ] 改造日常持久化检查点及完整备份，减少全量深拷贝和整包编码；验证耐久性、重启恢复及现有配置承诺。
- [ ] 在宿主现有管理 ABI 上验证分块下载端点，通过任务身份、范围、校验和和版本保证完整性；保持管理鉴权，并测量取消、重试、过期和下载耗时。
- [ ] 内置看板透明采用分块传输，保持原按钮、文件名、格式及交互；测量浏览器组装文件的峰值内存，避免重复解析、再编码整个导出文件。
- [ ] 对大文件导入验证分块上传、临时暂存、分批校验和原子提交，保持原导入计数及失败语义；数据库模式利用事务与暂存，内存模式单独控制临时副本。
- [ ] 保留旧整包接口及容量规则，分别测量其生成和传输峰值。宿主 ABI 仍要求完整响应缓冲的路径具有响应大小决定的内存下限，不以更换 JSON encoder 宣称恒定内存。
- [ ] 控制任务暂存及数据库读事务寿命，避免 WAL 持续增长；保持已有任务容量和目标负载下的完成时延，覆盖并发写入、导入、改价、修复和过期。

完成条件：常用大文件路径的服务端峰值内存下降，文件结果完整一致，用户操作和完成时延不退化；旧接口及内存模式的剩余开销有独立测量。
