## 1. 固定约束

- 部署只有一个 CPA 容器；统计插件、数据库引擎和后台任务均在 CPA 进程内运行，不新增数据库、缓存或任务服务容器。
- SQLite 引擎随插件交付，用户不需要安装数据库服务；数据沿用 `./data:/CLIProxyAPI/data` 挂载。
- 改造范围在插件内，保持插件 ID、宿主 ABI、已有管理接口和配置语义，不要求修改或重编译 CPA。
- 原生 usage 仍是唯一计数来源。请求数、成功失败、各类 token、延迟、TTFT、端点和流式元数据的现有语义保持兼容。
- 保持保留天数、可见明细条数、精简账本、导出容量和历史精确计价；真实重复请求继续保留，客户端身份继续精确区分。
- 保持看板筛选、排序、翻页、健康网格、趋势、币种切换、价格设置和导入导出的交互与结果。
- 保持当前前台 30 秒、后台 300 秒的轮询调度，以及手动刷新和切回页面的及时刷新行为。
- 保持请求记录的查询可见性、价格更新返回时的统计一致性、导入原子性，以及既有 flush、fsync 和恢复保障。
- `storage_enabled: false` 继续使用原有内存统计模式，不自动把 usage 历史写入数据库；既有价格文件及导出临时文件的行为保持兼容。
- 现有平台支持继续保留：Linux amd64/arm64、macOS amd64/arm64、Windows amd64。

目标部署结构：

```text
一个 CPA Docker 容器
└── CPA 进程
    └── usage-dashboard-zduu 插件
        ├── usage 接收、统计查询、内嵌看板
        ├── 有预算的缓存、后台写入、导入导出
        └── 内嵌 SQLite（持久化模式）

宿主机 ./data  <──挂载──>  容器 /CLIProxyAPI/data
```

### P6：快照、导入导出及分块传输

涉及：`go/stats.go`、`go/dashboard_export_jobs.go`、`go/management.go`、`go/main.go`、前端导入导出逻辑。

- [ ] 为导出冻结真实数据版本和价格版本；持久化模式使用一致性读取，内存模式使用有预算的不可变分段或等价方案。只冻结时间上界或最大 ID 不足以隔离后续修复、改价和删除。
- [ ] 分批生成 JSON、JSONL、CSV 和 gzip 文件，消除全部匹配记录的额外复制；保持事件、成本、字段、排序、计数、截断规则和原有下载文件结构。
- [ ] 改造日常持久化检查点及完整备份，减少全量深拷贝和整包编码；验证耐久性、重启恢复及现有配置承诺。
- [ ] 在宿主现有管理 ABI 上验证分块下载端点，通过任务身份、范围、校验和和版本保证完整性；保持管理鉴权，并测量取消、重试、过期和下载耗时。
- [ ] 内置看板透明采用分块传输，保持原按钮、文件名、格式及交互；测量浏览器组装文件的峰值内存，避免重复解析、再编码整个导出文件。
- [ ] 对大文件导入验证分块上传、临时暂存、分批校验和原子提交，保持原导入计数及失败语义；数据库模式利用事务与暂存，内存模式单独控制临时副本。
- [ ] 保留旧整包接口及容量规则，分别测量其生成和传输峰值。宿主 ABI 仍要求完整响应缓冲的路径具有响应大小决定的内存下限，不以更换 JSON encoder 宣称恒定内存。
- [ ] 控制任务暂存及数据库读事务寿命，避免 WAL 持续增长；保持已有任务容量和目标负载下的完成时延，覆盖并发写入、导入、改价、修复和过期。

完成条件：常用大文件路径的服务端峰值内存下降，文件结果完整一致，用户操作和完成时延不退化；旧接口及内存模式的剩余开销有独立测量。

### P7：回归、单容器压测与交付准备

- [ ] 运行 Go race、vet、JavaScript、更新脚本和未修改 CPA SDK 的 ABI 验证；补充本次实现涉及的精确统计、索引失效、迁移、恢复和传输回归。
- [ ] 完成现有五个平台的构建及相应装载检查，记录实际验证环境；单容器 Linux amd64/arm64 为重点部署验收场景。
- [ ] 使用 P0 相同配置和数据，重复测量空闲、持续/突发写入、多看板、冷热查询、改价、导入导出、清理和重启恢复。
- [ ] 核对所有功能结果一致；查询、请求回调、首屏、翻页、改价、下载及启动时延均满足 P0 固定标准。
- [ ] 分别报告稳定期及峰值 heap、RSS、容器内存、CPU、GC、磁盘和浏览器开销；达到 P0 固定的内存及 CPU 降低目标，而非仅降低单项 Go 分配量。
- [ ] 长时间运行并核对记录，验证内存不持续漂移、队列能回落、WAL 和暂存能回收，异常恢复仍符合现有可靠性要求。
- [ ] 更新单容器部署、挂载、升级、首次迁移、备份恢复及降级说明，记录性能数据、已验证环境和适用边界。
- [ ] 汇总完成项与遗留项，全部验收通过后形成可交付实现；本临时清单本身不表示已执行提交、发布或部署。

完成条件：同一单容器、同等数据量、同等功能与体验下，内存和 CPU 的下降已验证，升级与恢复路径已演练。

## 6. 统一一致性与后端契约

- 定义内部记录 ID 与内容版本；记录 ID 不等于内容去重键。实时相同内容的真实请求拥有不同 ID；导入/重放按现有来源和去重规则处理。
- 分离已接收、查询可见、事务已提交、达到当前同步配置耐久点四种状态。记录回调返回后的可见性保持现状；数据库尚未提交的数据必须由同版本、有预算的覆盖层精确合并。
- 缓存键至少受查询参数、数据版本、价格版本和时间桶约束；币种变化只影响相关展示，但不能让同一响应混用不同汇率或价格。
- 内存后端通过不可变分段/受控锁保护、数据库后端通过事务/快照获得一致读视图；禁止复制一半后释放锁继续读取可变数据。
- 新增、迟到、元数据、修复、删除、到期、导入、改价和配置变化必须有事件索引、汇总、缓存、持久化影响矩阵，覆盖所有后端。
- 改价期间在旧版本基础上计算新版本并追赶增量；发布时原子切换。保持同步管理接口现有语义和保存失败行为。若无法满足超时，继续优化或明确提出交互变更，不默认改为异步成功。
- 配置切换与关闭定义停收、排空、最终同步、任务取消和资源释放顺序；不得持有统计锁等待需要同一锁的后台工作。

## 7. 资源预算与超限行为

P0 必须填写各预算的数值、计量方式、预警点、回收策略和配置来源。现有 8/32 MiB 仅是局部预算，不是总预算；下列未定数值属于实施前必须解决的设计项，不得带着空值宣称资源受控。

| 资源 | 当前/起始边界 | 实施与超限处理 |
| --- | --- | --- |
| 事件结果 | 已有 8 MiB 估算 | 加入全局预算，未命中可重算；估算包含保留字符串与键，不作为实际 RSS |
| 事件索引 | 已有数组 32 MiB、32 个维度键、4096 条待更新 | 计入 ID/身份映射与共享引用的实际持有；可回收重建，不改变查询结果 |
| 近期明细、汇总、身份字典 | P0 按数据分布确定字节数 | 数据库模式超限逐出缓存后按需读盘；纯内存权威历史不能当缓存删除 |
| 待提交与查询覆盖层 | P0 确定字节、条数及最长等待 | 队列与覆盖层共享计量，防止双份无界复制；超负载采用可观察背压，保留同步配置承诺 |
| 编码与批处理缓冲 | 已有计划：可复用编码缓冲 ≤256 KiB | 超大单条采用临时受控处理或磁盘暂存；不能静默拒绝原先合法记录，大对象不留池 |
| SQLite 原生内存 | P4 前固定总页缓存、读连接数、mmap 与临时排序策略 | 页缓存按所有连接总量计量；不能仅看 Go heap；单写入协调器，读连接有上限 |
| 导出任务 | 保持现有 2 个活动任务、16 个保留任务容量 | 另设工作内存和暂存磁盘预算，任务冻结状态、文件、下载生命周期共同计量 |
| WAL、迁移、备份和暂存文件 | P0/P4 固定磁盘预算及空间预留 | 观测增长速率与检查点受阻；有界等待/取消任务并清理自有暂存，不删权威数据 |
| 前端缓存与下载 | P0 记录峰值与缓存容量 | 淘汰失效结果、释放 Blob/object URL，分块重试不重复组装整文件 |

需要报告的峰值包含：活跃数据 + 所有缓存 + 待提交数据 + 并发查询/导出工作区 + 数据库原生内存 + ABI 编码缓冲；记录 OS 页缓存及容器计费口径。`GOMEMLIMIT` 仅可作为测量后的补充，不是进程硬上限，也不能修改共享 CPA 进程的全局 GC 参数来制造插件收益。

## 9. 最小验收矩阵与阶段交付

以下各轴做风险驱动组合，关键交互必须覆盖；无需机械运行全部笛卡尔积，但不得遗漏已知风险。

- 后端：纯内存、现有 JSONL 持久化兼容路径、SQLite；初次迁移、常规重启、异常恢复。
- 数据：10 万/100 万、低/高维度、长错误与头、旧聚合残差、已归档账本、迟到和真实重复。
- 请求：空闲、低频、稳定写入、突发超过磁盘承载、多看板并发和相反顺序返回。
- 查询：无筛选、时间、API/模型/来源/凭证/客户端及组合、深分页、冷热缓存、窗口跨界。
- 状态变化：写入时改价、再次改价、导入时刷新、导出时修复/到期、重载时排队、关闭时取消。
- 文件：旧/新快照、重叠 JSONL、缺失/损坏/权限/磁盘满、备份期间写入、下载过期/重试。
- 平台：五种交付目标；Linux amd64/arm64 单 CPA 容器为重点，构建证据不替代装载证据。

每阶段按“证据→设计决定→小步实现→回归→性能对比→复查修复”交付。P7 将所有覆盖项映射到 G01–G08，失败项返回相应阶段处理。可以提供明确标注限制的测试产物收集反馈，但正式版与“全面优化完成”结论必须等所有门槛通过。
